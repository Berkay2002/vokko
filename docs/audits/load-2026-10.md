# Load audit, October 2026

Tool: `tools/loadtest` (`vokko-loadtest`, see its README). Server: `crates/server` at origin/main 010215e. Raw results: `tools/loadtest/results/2026-10/` (`experiments/` holds the side runs quoted below).

## Setup

| | |
| --- | --- |
| Machine | cloud sandbox, 4 vCPU Xeon 2.1 GHz (no SMT), 16 GB RAM, loopback network |
| Server | `cargo build --release -p vokko-server`, `VOKKO_TRUST_PROXY=on VOKKO_UNFURL=off`, otherwise defaults (DB pool 10, replay buffer 1000, rate limits on) |
| Database | PostgreSQL 16.13 from apt, stock config (`shared_buffers` 128 MB, `max_connections` 100, fsync on, ~0.28 ms per fsync), fresh database per run, same machine |
| Load generator | `vokko-loadtest`, same machine, so **server, Postgres and the generator share the 4 cores** |
| Population | N users registered over REST, guilds of 100 members (one run: one guild of 1000), 3 text channels each, every user holds one gateway connection |
| Scenarios per run | connect, send (20% of each guild posts 1 msg/s), typing (30% fire one typing request per second, all at the same instant), presence (50% change presence 3 times, then clear), history (20% page back 10 × 100 messages), reconnect (50% of connections cut for 2 s, then Resume, while the send load continues) |

**Scale.** The 50/200/1000 connection counts are the real thing, no scale-down was needed for connections. What is scaled down: each scenario lasts 15-20 s (not minutes), the sender/typer/reader shares are fractions of the population, and absolute numbers are a floor for a dedicated server host because the generator and Postgres compete with the server for the same four cores (`vmstat` during the saturated send runs: 13-20 % idle, run queue 5-10, 27 % system time, 50-70 k context switches/s). The 1000-in-one-guild run uses smaller sender/typer/reader shares (2 % / 3 % / 5 %) because every message there fans out to 1000 receivers. Its rows are not comparable to the guild-of-100 columns for send/typing/history. No visual or client-side behaviour is covered.

**Limits.** No run touched a limit: 0 HTTP 429, 0 gateway 4008, 0 other errors in all four runs. How the harness stays under them (docs/api.md "Limits and abuse controls"):
- Per-user REST buckets: sends ≤ 5/s, typing 1/s, history ≤ ~6/s per user (limits are 10/s per route, 50/s overall).
- Gateway: Identify once per session (the reconnect storm uses Resume, Identify only after InvalidSession), op 3 four times per session (limit 5/min).
- Per-address limits (`/auth/*` burst 10 then 1 per 2 s; 16 unidentified sockets) cannot be met by one machine registering 1000 users: that would take ≥ 33 minutes. The server exposes `VOKKO_TRUST_PROXY=on` for deployments behind a proxy, and the harness uses it: each simulated client sends its own `X-Forwarded-For`. This is the only limit-related setting changed. Evidence that the limits do bite otherwise (`--no-spoof`, 30 users, `experiments/nospoof.json`): registration needed 44 s with 106 × 429 waited out, and only 16 of 30 gateway sockets opened (14 × HTTP 429 on the upgrade).
- The REST rate-limit values, the DB pool size (10, `lib.rs connect`) and the replay buffer size (1000) are not configurable at runtime, so no scenario was run with raised limits. Nothing needed it.

## First bottleneck: CPU spent per message and per delivered event

Everything stays correct up to 1000 connections; what gives out first is throughput of the send path, and what grows fastest with connection count is the latency of synchronized bursts. Offered send load at 1000 connections, guild size 100 (`experiments/ramp_*.json`, `sat_g50.json`):

| offered | achieved | send REST p50 | server / Postgres / generator CPU (avg) |
| --- | --- | --- | --- |
| 175 msg/s (17.5 k deliveries/s) | 175 msg/s | 14 ms | 110 / 56 / 40 % |
| 500 msg/s (50 k/s) | **328 msg/s** (32.8 k/s) | 3 629 ms | 161 / 74 / 62 % |
| 1000 msg/s (100 k/s) | **321 msg/s** (32.1 k/s) | 24 788 ms | 170 / 77 / 64 % |

Evidence that this is aggregate CPU and not one lock, the DB pool or the disk:
1. Doubling the offered load does not raise throughput (328 → 321 msg/s) and latency becomes queue length (3.6 s → 25 s).
2. The box is CPU-bound while no single process is: `vmstat` shows 13-20 % idle, run queue 5-10 on 4 cores, 27 % system time, 55-70 k context switches/s.
3. DB pool 10 → 40 (temporary local patch of `lib.rs`, not in this PR): ceiling unchanged (328 → 325 msg/s), typing p50 unchanged (269 → 269 ms), identify and send unchanged. The pool only matters for history: page p50 129 → 69 ms (`experiments/cmp_*.json`, `ramp_pool40.json`).
4. fsync is not it: `pg_test_fsync` gives 3.5 k ops/s (0.28 ms), the ceiling is 330 commits/s.
5. Linear fit of the seven send windows (`sat_g50`, `ramp_0.5`, `sat_g1000a`, `r200`, `r1000`, `r1000big`, `sat_g1000b`; max error 26 % of a core): the server needs **≈ 2.3 ms CPU per message plus ≈ 26 µs CPU per delivered event**, Postgres ≈ 2.2 ms per message (≈ 13 queries per send), the generator ≈ 17 µs per received event. For a 100-member channel that is 4.9 ms server + 2.2 ms Postgres ≈ 7 ms per message (≈ 560 msg/s on 4 dedicated cores; 330-400 measured with the generator on the same cores). In a 1000-member channel the per-delivery term is 26 ms against 2.3 ms, so fan-out dominates from guilds of a few hundred members.
6. The same cost explains the burst behaviour: 300 typing requests in one instant need 300 × (≈ 2.4 ms server + ≈ 0.7 ms Postgres + generator) ≈ 1.2 core-seconds, which the four cores give back in ≈ 0.3 s: typing p50 11 → 48 → 277 ms at 50 / 200 / 1000 connections, with average CPU still at 73 % of one core. Accepting an invite (673 ms at 10 × 32 concurrent joins) and history pages (183 ms with 200 concurrent readers) are the same pattern.

I did not profile (no `perf` in the sandbox), so the split between "serialization" and "socket syscalls" inside the 26 µs is inferred from code and the 27 % system time, not measured.

### Second finding: memory per session is O(READY + 1000 events), RSS reaches 1.1-1.4 GB at 1000 sessions

RSS after connecting 1000 clients: 380 MiB with guilds of 100, **1006 MiB** with one guild of 1000, before a single message is sent; it keeps growing while events flow until every session's replay buffer is full (peak 733 MiB at the default load with guilds of 100, 1.0-1.4 GB in the saturated and the 1000-member runs). Causes in `hub.rs`/`gateway.rs`:
- `Session::push` stores a private copy of every serialized frame per session (`buffer` of 1000 entries, plus a second clone for the queue), so memory is sessions × 1000 × frame size even though the payload is identical for every recipient.
- READY goes through the same buffer (`gateway.rs handshake`: `session.dispatch("READY", …)`), and is kept until 1000 newer events push it out; READY is 309 KiB with a 1000-member guild.
- Experiment (temporary patch: send READY with a sequence number but do not buffer it): RSS after connect drops by ≈ 300 MiB (831 → 526 MiB growth over the idle server), which is READY size × sessions (`experiments/rdy_*.json`). The remaining 526 MiB are the presence events every connect fans out (520 k received by clients in this run) plus transient READY building; I did not separate those two.

### Third finding: a reconnect storm is amplified by presence flapping

Every cut and every Resume flips the user's presence for the whole audience (`gateway.rs handle`: `hub.connection_closed` → `presence::disconnected` broadcasts offline, `connection_opened` → `presence::connected` broadcasts online), even when the session resumes two seconds later without losing anything. Cutting 500 connections therefore produced 100 000 PRESENCE_UPDATE deliveries with guilds of 100 and **1 000 000 with one guild of 1000** (500 × 2 × 1000), against 260 000 message deliveries in the same window (`reconnect` rows of `r1000.json`, `r1000big.json`: counter `recv:presence_other`). This, plus the replay of the buffered events, is why Resume takes 1.5 s p50 / 2.9 s p99 in the 1000-member guild against 0.34 s / 0.53 s with guilds of 100. (An earlier draft of these notes blamed READY size; Resume does not send READY.)

### Unconfirmed

Once (200 connections, 100 resumes, before the counter was split into out-of-order and skipped) two dispatches arrived non-consecutively after a Resume. The final eight runs show 0 out-of-order and 0 skipped. A plausible cause is the race in `gateway.rs` Resume handling: `session.attach(link)` and `session.replay_after(seq)` take the session lock separately, so a live event pushed in between is both queued live and replayed (duplicate or reordered `s`). I could not reproduce it, so it is a lead, not a finding.

## Suggestions for the server worker

In rough order of expected payoff (1-4 are CPU and memory per delivery; 5-6 are the join/identify path; 7-10 are scaling hazards and tunables), each tied to the measurements above; none is applied here.

1. **Serialize an event once, not once per recipient** (`hub.rs` `Hub::send_with`, `Session::push`; `routes/messages.rs` `insert_message`, closure passed to `send_with`). Today every recipient gets `serde_json::to_value(view.for_viewer(user))` followed by `to_string`. Messages without reactions are identical for all viewers; render the `d` part once into an `Arc<str>` and let each session splice its own `s` (`{"op":0,"d":…,"s":N,"t":"…"}`). Removes most of the ≈ 26 µs per delivery and the per-session `Value` clones.
2. **Buffer shared payloads, not frames** (`hub.rs` `SessionInner::buffer`): keep `(seq, Arc<str>)` for the shared `d`, build the frame at send/replay time. Cuts replay memory from sessions × 1000 × frame to sessions × 1000 × pointer. Do not buffer READY (`gateway.rs handshake`, Identify branch): a resume never needs it (it re-identifies instead).
3. **Fewer queries per message and per typing event** (`access.rs` `channel_access` + `channel_viewers`, `routes/messages.rs` `insert_message`/`typing`, `store.rs` `message_view`): `overwrites_for` runs twice per send, `channel_viewers` reads the whole member and member-role tables of the guild on every message and every typing event, and `message_view` re-reads the row that was just inserted. Cache `(members, roles, overwrites)` per guild/channel in `AppState`, invalidated by the existing role/overwrite/member mutations; build the view from the inserted values. Target: the ≈ 2.2 ms of Postgres CPU per message and most of the 2.4 ms per typing request. Typing needs only the viewer set, not channel permissions beyond SEND_MESSAGES.
4. **Batch socket writes** (`gateway.rs` `run`, the `receiver.queue.recv()` arm): drain with `recv_many`, `feed` the frames and flush once. The send path costs 27 % system time and 55-70 k context switches/s at 33 k deliveries/s; fewer flushes is the cheapest way to cut that.
5. **READY size and cost** (`gateway.rs` `build_ready`, `events.rs` `guild_with_state`): READY carries every member (up to 10 000 per guild, 309 KiB at 1000 members, identify p50 693 ms with 100 concurrent identifies). Send the member list lazily, or at least cap it; at 10 000 members one READY is ≈ 3 MB and N reconnecting clients cost N × that, which is what a mass re-identify (Resume fallback after a server restart, where sessions are gone) would cost.
6. **Invite accept** (`routes/invites.rs` `accept`): 673 ms p50 at 10 guilds × 32 concurrent joins. It returns `guild_with_state` (all members) to the joiner and sends GUILD_MEMBER_ADD plus a system message to everyone: same READY-size problem, plus `access::guild_member_ids` per join.
7. **Sessions index** (`hub.rs` `Hub::send_with`): every event scans all sessions under one mutex (`sessions.values().filter(wanted.contains)`). Irrelevant at 1000 sessions, O(sessions × events) beyond ~50 k. Keep a `user_id → [Arc<Session>]` map. Not measured here.
8. **Expose tunables** (`lib.rs connect` pool size 10, `Config` replay capacity and rate limits): environment variables for pool size and a documented "rate limiting off" switch for benchmarks would let the next audit run without touching code. The pool halves history page latency at 40 (129 → 69 ms) and is otherwise not a bottleneck here.
9. **Presence grace period** (`gateway.rs handle`, `presence.rs` `disconnected`/`connected`, `hub.rs` `connection_closed`): do not broadcast offline until the session has been detached for a few seconds (the replay session already survives `session_ttl` 300 s); a Resume inside the grace period then sends nothing. Removes the 1 M-event amplification above.
10. **Registration/login throughput** (`auth.rs`): argon2 with 4 concurrent hashes saturates all four cores (335 %) at ~150 hashes/s. Fine for humans, a limit for a login storm after a restart. Tokens are opaque and survive restarts, so clients only re-login when a token is revoked.

## Reproducing

```sh
sudo service postgresql start
sudo -u postgres psql -c "create user vokko with password 'vokko' createdb;" -c "create database vokko_load owner vokko;"
export DATABASE_URL=postgres://vokko:vokko@127.0.0.1:5432/vokko_load VOKKO_TRUST_PROXY=on VOKKO_UNFURL=off
cargo build --release -p vokko-server -p vokko-loadtest
./target/release/vokko-server &
./target/release/vokko-loadtest --connections 1000 --duration 20 --server-pid $(pgrep -x vokko-server) --sample-postgres --out run.json
# one guild of 1000 (smaller shares, see Setup)
./target/release/vokko-loadtest --connections 1000 --guild-size 1000 --sender-fraction 0.02 --typing-fraction 0.03 --presence-fraction 0.05 --history-fraction 0.05 --duration 20
```
Use a fresh database per run (users are named `lt<run>_<n>`, reruns on the same database work but history and READY sizes grow).
