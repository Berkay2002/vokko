# Vokko server API (v1 contract)

Types: `apps/desktop/src/api/types.ts` is the source of truth for JSON shapes until generated bindings replace it. The Rust side (`crates/protocol` `api` module) must serialize identically. Shapes follow Discord's public API where it fits, so behaviour can be compared one to one.

General rules:
- Base URL `http://<host>:<port>/api/v1`. Auth header `Authorization: <token>` (opaque session token, no "Bearer" prefix, Discord-style). Everything except `/auth/*` requires it.
- IDs are 64-bit snowflakes (Discord epoch 2015-01-01, worker/process bits, increment) serialized as strings.
- Errors: HTTP status + `ApiError` body. 400 → 50035, 401 → 0 "401: Unauthorized", 403 → 50001/50013, 404 → 10003 (channel), 10008 (message), 10004 (guild), 10013 (user).
- Server is authoritative for every permission check. Message content max 2000 chars, trimmed, not empty unless attachments exist.
- CORS allows `http://localhost:*`, `http://127.0.0.1:*` and `tauri://localhost` / `http://tauri.localhost` in dev. `VOKKO_CORS_ORIGINS` (comma-separated exact origins) replaces the localhost part; the Tauri origins always stay allowed.
- `GET /healthz` (outside `/api/v1`, no auth, no rate limit): `200 {status: "ok", version, db: "ok"}`, or `503 {status: "unavailable", version, db: "error"}` when the database does not answer within 2 s.
- With `VOKKO_REGISTRATION=closed`, `POST /auth/register` answers `403` with code `40002` ("Registration is closed on this server"); login and existing sessions are unaffected.
- Profile images (avatar, banner, server icon, per-server avatar/banner) must be PNG, JPEG, GIF or WebP; the server stores them as uploaded (no resize): avatar/icon at most 8 MiB (animated GIF 2 MiB), banner at most 10 MiB (animated GIF 4 MiB), otherwise 400 / 50035 on the `*_attachment_id` field. `pronouns` ≤ 40 characters, `bio` ≤ 190, server tag 1-4 non-space characters, decoration / effect / badge / preset ids are 1-64 characters of `a-z 0-9 _ -`, colours are RGB ints (0..16777215).
- Profile widgets (`User.widgets`, always sent, `null` when none): `{favorite_game?: {name, image, image_attachment_id, reason, tags}, games_i_like?: [{name, image, image_attachment_id}]}`. `PATCH /users/@me` takes `widgets: {favorite_game?, games_i_like?} | null`: the value replaces the whole board (a missing key means none), `null` (or an empty object) clears it, an absent `widgets` leaves it. Entries are `{name, image_attachment_id?}` (favourite also `reason?`, `tags?`); the image is one of the caller's own uploads (PNG, JPEG, GIF or WebP, limits of an avatar), and echoing the `image_attachment_id` of an image already on the board keeps it. Limits: unknown keys other than `favorite_game` / `games_i_like` are refused, `name` 1-64 characters (trimmed), `reason` ≤ 190 (empty clears), `tags` ≤ 5 each 1-20 characters and unique (case-insensitive), `games_i_like` ≤ 20 entries; failures are 400 / 50035 keyed by path (`widgets.favorite_game.reason`, `widgets.games_i_like.3.image_attachment_id`). An upload that the board stops showing goes back to being a pending upload (removed by the periodic cleanup) unless an avatar, banner, server profile, icon or another widget still uses it. Event covers and sticker images are refused as profile images.
- A user's `primary_guild` is only reported while they are still in that guild and the guild still has a tag; leaving, being kicked or banned, or the tag being removed clears it and sends USER_UPDATE (editing a tag sends USER_UPDATE for everyone wearing it).

`ThreadMember` is `{id (thread), user_id, join_timestamp, flags, muted, mute_config}`. `flags`: HAS_INTERACTED 1<<0 (kept as stored), ALL_MESSAGES 1<<1, ONLY_MENTIONS 1<<2, NO_MESSAGES 1<<3; none of the last three set = the thread uses its parent channel's setting. `mute_config` is `{end_time: ISO8601 | null}` (the same `MuteConfig` as user guild settings; null `end_time` = until turned back on) or null when not muted; a timed mute whose `end_time` has passed reads as `muted: false, mute_config: null` (computed on read). `muted: true` with `mute_config: null` in a PATCH mutes forever. GET members, THREAD_MEMBER_UPDATE and the `member` on thread/channel payloads all carry these fields.

## Invites and server folders

- **Create.** `max_age` 0..604800 s (0 = never, default 86400; the client offers 30 min, 1 h, 6 h, 12 h, 1 d, 7 d, never), `max_uses` 0..100 (0 = no limit, default 0; the client offers 1, 5, 10, 25, 50, 100), `temporary` (default false), `unique` (default false). Out of range → 400 50035. Without `unique: true` the server returns an existing live invite of the same inviter and channel with identical `max_age`, `max_uses` and `temporary` (no INVITE_CREATE then). Threads and DMs cannot have invites (400 50035).
- **Expiry and uses.** An invite past `expires_at` or with `uses >= max_uses` (when `max_uses > 0`) is gone: preview/accept/revoke → 404 10006, and it is not listed. Accepting counts a use in the same transaction as the member insert with a conditional update, so concurrent accepts never exceed `max_uses`; an existing member accepting does not use it up.
- **Temporary membership.** Joining through a `temporary` invite marks the membership temporary. When the user's last gateway connection closes, every temporary membership of theirs that has no role is removed like a kick (GUILD_DELETE to them, GUILD_MEMBER_REMOVE to the guild). A member who has any role at that moment stays (still temporary); accepting a normal invite makes the membership permanent. A user who never connects to the gateway is not removed until a connection of theirs closes.
- **Listing and revoking.** `GET /guilds/{id}/invites` needs MANAGE_GUILD, `GET /channels/{id}/invites` MANAGE_CHANNELS on that channel; `DELETE /invites/{code}` either of the two. Lists are oldest first, live invites only, with `inviter`, `uses` and `created_at`. INVITE_CREATE / INVITE_DELETE go to guild members who could list the invite (MANAGE_GUILD, or MANAGE_CHANNELS on its channel); an invite that expires or is used up sends nothing.
- **Guild layout (server folders).** `guild_folders`: up to 100 `{id, name, color, guild_ids}`, `id` chosen by the client (snowflake string, unique), `name` 1-32 chars or null (blank → null), `color` RGB int or null, `guild_ids` 1-200 with no guild in two folders and at most 1000 guild ids across all folders. `guild_positions`: up to 1000 guild ids, no duplicates, the rail order (guilds missing from it follow in join order; a folder sits where its first guild is). Guild ids are not checked against membership (stale ones are ignored by the client). Invalid → 400 50035 and nothing changes. READY carries `guild_layout`; PATCH sends GUILD_LAYOUT_UPDATE (the full layout) to all of the user's sessions.

## Community features (scheduled events, onboarding, friend suggestions)

Scheduled events (Discord shape; permissions CREATE_EVENTS 1<<44 and MANAGE_EVENTS 1<<33, CREATE_EVENTS is in the default @everyone set):
- `entity_type` 1 stage / 2 voice need a `channel_id` of a voice channel on which the caller has VIEW_CHANNEL + CONNECT (Vokko has no stage channels yet, so type 1 also points at a voice channel); 3 external needs `entity_metadata.location` (1-100 chars) and `scheduled_end_time`. Type 3 must not carry a channel. `name` 1-100 chars, `description` max 1000, `scheduled_start_time` must be in the future on create, an end time must be after the start, `privacy_level` is 2 or absent. A cover is a pending attachment (`image_attachment_id`, PNG/JPEG/WebP/GIF with the banner caps: 10 MiB, animated 4 MiB); `image` is its URL. A cover belongs to its event alone: an upload already used as an avatar, icon or another cover is refused (400 50035; sending the event's own current cover again is accepted), and the other way round an avatar, icon or banner refuses an upload that serves as a cover (an upload that is already claimed as an avatar, icon, banner or cover is also refused as a message attachment, and deleting a channel, thread or guild it came through keeps it), the file survives deleting the channel it came through, and it is deleted when the cover is replaced or cleared, or the event or guild is deleted.
- Status moves only Scheduled → Active, Scheduled → Canceled, Active → Completed (anything else 400 50035 on `status`); a Completed or Canceled event is frozen (edits and Interested → 400 180000) but can still be read and deleted. Entity type, channel, start time and recurrence can only change while Scheduled. Nothing starts or ends events on a timer: someone with permission sends the status change.
- `recurrence_rule` is stored and returned (frequency, interval 1-12, `by_weekday` 0 = Monday, optional `end`/`count`); Vokko does not generate follow-up occurrences yet, clients show it as text.
- `user_count` counts Interested members; `user_rsvp` is filled per receiver, also on gateway events. Interested rows go away when the user leaves, is kicked or banned. Deleting the channel an event points at clears its `channel_id` (the event stays, GUILD_SCHEDULED_EVENT_UPDATE is sent).
- Visibility follows the channel. External events belong to the whole guild. An event in a voice (or stage) channel exists only for members who can view that channel: it is left out of the list, GET, edit, delete, the Interested routes and the Interested list answer 404 10065 for everyone else, and every GUILD_SCHEDULED_EVENT_* dispatch (create, update, delete, user add/remove) goes only to those who can view it. When the channel is deleted the event keeps living without a `channel_id`, visible only to its creator and people with MANAGE_EVENTS: others who saw it through the channel get a DELETE, the rest an UPDATE. Such an event can still be edited (renamed, rescheduled) without picking a channel, but it cannot be started (400 50035 on `channel_id`), and picking another entity type or channel needs a valid voice channel.
- Starting, ending or canceling an event (a `status` change) re-checks that the caller can still CONNECT to its channel (403 50013). `status: 2` together with a different `scheduled_start_time` is refused (400 50035): start it or move it. Max 100 non-finished events per guild (400 30038), counted under a lock so concurrent creates cannot exceed it. Editing an event into a channel some of its viewers cannot view sends those viewers GUILD_SCHEDULED_EVENT_DELETE (everyone who can view it afterwards gets the update).

Onboarding (Discord shape): `GuildOnboarding` holds up to 15 prompts (multiple choice or dropdown, 1-50 options each; option titles 1-50 chars, descriptions max 100), up to 50 default channels, `enabled`, `mode` and an optional rules screen (`rules.items` 1-16 entries). Configuring needs MANAGE_GUILD **and** MANAGE_ROLES; an option may only grant roles that exist, are not @everyone and sit below the editor's highest role (owner exempt), channels must be text or voice channels of the guild. `channel_ids` never changes permissions: it says where to send the member, and completion filters it by what the member can view. Prompt/option ids sent back are kept, unknown or absent ones are created with new ids; options that disappear lose the answers members gave for them (roles already granted stay). A role a moderator later removes from or hands to a member through `PATCH /guilds/{id}/members/{uid}` stops counting as granted by onboarding, so a later answer never takes it away.
- When a member joins (invite) a guild with onboarding enabled the server sets `STARTED_ONBOARDING` (1<<3) on `GuildMember.flags`; members who were there earlier are never prompted. The client shows the flow while STARTED is set and COMPLETED_ONBOARDING (1<<1) is not.
- `PUT /guilds/{id}/onboarding-responses` replaces the caller's answers: option ids must belong to the guild's prompts, `single_select` prompts take at most one, `required` prompts at least one (400 50035 on `option_ids`); with rules configured `rules_accepted` must be true (400 50035 on `rules_accepted`); onboarding disabled → 400 50035. Roles of newly chosen options are added; what onboarding added is remembered per member, so a role is taken back only when no chosen option grants it any more and onboarding was what gave it (a role the member held already is never removed, whatever the options say now); then `COMPLETED_ONBOARDING` is set and GUILD_MEMBER_UPDATE is sent. The answer is atomic. `OnboardingCompletion.channel_ids` lists the default channels that the member can view and, only in `Advanced` mode (1), then the chosen options' channels; `Default` mode (0) lands the member in the default channels alone.

Friend suggestions: candidates are users who share a guild of at most 200 members with the caller, or who are friends of the caller's friends. Never listed: the caller, bots, anyone with any relationship to the caller (friend, pending either way, blocked either way), anyone who blocked the caller, anyone with suggestions switched off, anyone the caller dismissed. Switching suggestions off (default on) empties the caller's own list and removes them from everybody else's, in one setting. `mutual_friends_count` is the profile's count (GET /users/{id}/relationships): 0 for a friend of a friend who shares no guild or DM with a message with the caller, so a suggestion never shows more than the profile. Order: that count first, then mutual small guilds, then user id (hidden counts do not rank); `limit` 1-100 (default 25). `mutual_guilds` lists only guilds the caller is also in.

## Members page (member-safety search)

`POST /guilds/{id}/members-search` is Discord's member-safety search. Access: any of ADMINISTRATOR, MANAGE_GUILD, KICK_MEMBERS, BAN_MEMBERS, MODERATE_MEMBERS, MANAGE_ROLES, MANAGE_NICKNAMES (Discord's member-safety access check), else 403 50013; non-members 403 50001.
- Body `{limit?, offset?, sort?, and_query}`. `limit` 1-1000 (default 25), `offset` 0-100000 (default 0; Vokko pages by offset so the UI can jump to a page, Discord uses `before`/`after` cursors, which Vokko does not take). `sort`: 1 member since newest first (default), 2 member since oldest first, 3 joined Vokko newest first, 4 joined Vokko oldest first; ties break on user id in the same direction.
- `and_query` (every present key must match; absent or empty = no filter): `usernames.or_query` (1-10 terms, each 1-100 chars, trimmed): case-insensitive prefix of the username, global name or nickname, or, for an all-digit term, the exact user id; `user_id.or_query` (ids); `role_ids.or_query` (has any) and/or `role_ids.and_query` (has all); `guild_joined_at.range` and `user_created_at.range` `{gte?, lte?}` inclusive unix ms (account creation is read from the snowflake); `source_invite_code.or_query`; `join_source_type.or_query`. Lists hold at most 100 entries. Invalid values → 400 50035.
- Response `{guild_id, members: [{member, source_invite_code, join_source_type, inviter_id}], page_result_count, total_result_count}`: `total_result_count` counts every match before offset/limit.
- Join source: accepting an invite as a new member stores `source_invite_code`, `inviter_id` (the invite's creator) and `join_source_type` 5 (INVITE) on the membership. Everyone else (the owner, members from before tracking, seeded members) has `null`, `null`, 0 (UNSPECIFIED), shown as "Unknown". Leaving and rejoining through another invite records the new one.

## Stickers, GIFs, forward, bookmarks, reminders

Vokko is free: nothing here is gated behind a plan. Server-side limits (sticker count per server, favourites) are plain config.

**Stickers.** Guild stickers in Discord's shape (always guild stickers, so no `type`). Formats: PNG, APNG (PNG with an `acTL` chunk), GIF, WebP; at most 512 KiB and 512x512 px; no Lottie. A sticker is created from a pending upload (`attachment_id`, uploaded like a guild icon) and is served from the usual `/attachments/...` URL. `name` 2-30 chars, `description` ≤100, `tags` 2-200 chars (comma separated; the picker searches name and tags). At most 60 per guild (400 code 30039). Sending: `CreateMessageRequest.sticker_ids` (max 3, content may be empty). A sticker of the channel's own guild always works; a sticker of another guild works when the sender is a member of that guild and holds USE_EXTERNAL_STICKERS in the channel (DMs: always), otherwise 403 50013; unknown sticker → 400 50035. Messages carry `sticker_items` (`id`, `name`, `format_type`, `url`) when they have stickers. Stickers live on in sent messages after the sticker is deleted (the item is a copy); deleting a guild removes its stickers. READY/GUILD_CREATE guild objects carry `stickers`; changes arrive as GUILD_STICKERS_UPDATE with the full list. `has=sticker` in message search matches messages with sticker items.

**GIFs.** The server proxies a provider so the API key never reaches a client: `VOKKO_GIF_PROVIDER=klipy|giphy|tenor|none` (default `none`), `VOKKO_GIF_API_KEY`, optional `VOKKO_GIF_BASE_URL` (override of the provider API origin, used by tests and mirrors). With `none` every `/gifs/search|trending|categories` answers an empty page with `provider: "none"` and the picker shows favourites only. Provider results are normalised to `Gif` (`id` is `<provider>:<provider id>`; `url` is the direct media URL, `preview_url` a small image); the client never talks to the provider. A provider failure → 502 with code 0. Sending a GIF is a normal message whose content is `Gif.url`; the link unfurl turns it into an image/gifv embed and the client hides a URL that is the whole content. Favourites are stored per user (the whole `Gif` is saved, so they keep working if the provider drops the item).

**Forward.** `POST /channels/{id}/messages` with `message_reference: {type: 1, message_id, channel_id}` copies the source message into the target channel as a message of type 0 with `message_reference.type = 1` (source ids, `guild_id` of the source channel) and one `message_snapshots` entry (content, attachments, embeds, stickers, timestamps, mentions; the author is not included, like Discord). A forward must not carry `content`, `attachment_ids` or `sticker_ids` (400 50035); the optional comment is a separate message sent by the client. The target channel's rules apply as for a normal post: a snapshot with attachments needs ATTACH_FILES there, and one with stickers from another server needs USE_EXTERNAL_STICKERS (DMs and the sticker's own server excepted), otherwise 403 50013; nothing is copied when a check fails. The caller needs VIEW_CHANNEL + READ_MESSAGE_HISTORY on the source channel; every reason the caller cannot read the source (unknown channel, no access, no READ_MESSAGE_HISTORY, unknown message) answers the same 404 10008 `Unknown Message`. The snapshot is a copy: editing or deleting the source later changes nothing. Forwarded attachments are copied to new files, so deleting the source does not break them. The client forwards to at most 5 destinations (one request each); the server does not count the destinations, but every forward is an ordinary post and is rate-limited like one. File copies are hard links where the filesystem allows, full copies otherwise. A forward of a forward copies the snapshot content (not the original ids). Snapshot mentions never ping. System messages cannot be forwarded and a forward cannot be edited (400); deleting a forward removes its file copies.

**Bookmarks** are per-user saved messages. A bookmark is only listed while the owner can still read the message (left the guild, lost the channel → hidden, not deleted); deleting the message removes the bookmark.

**Reminders.** The client turns presets (30 min, 1 h, 4 h, tomorrow 09:00, next Monday 09:00, custom) into an absolute `remind_at`. A background task (every `VOKKO_REMINDER_POLL_SECS`, default 15) marks due reminders delivered exactly once and sends REMINDER_DUE to the owner's sessions: this is the "notice from the instance"; it is not a real DM channel. Delivered reminders stay in `GET /users/@me/reminders` (inbox) until `DELETE`. If the owner can no longer read the message, `message` is `null`. Deleting the message removes the reminder.

Non-Discord error codes: 30090 bookmark limit, 30091 reminder limit, 30092 favourite GIF limit (500). 30039 is Discord's own sticker limit code.

## Soundboard and entrance sounds

Vokko is free here too: every guild has the top tier (48 sounds), any member can use any of their servers' sounds in any voice channel they are in, and everyone can set an entrance sound (per guild, plus a global fallback). Discord's shapes, with Vokko additions marked in types.ts (`url`, `sound_url`, `source_guild_id` and `entrance` on the effect).

- **Sounds.** A sound is created from a pending upload (`attachment_id`, uploaded like a sticker) and served from the usual `/attachments/...` URL (`url`). Formats: MP3, OGG (Vorbis or Opus) and WAV (PCM), detected from the file, not the content type; at most 512 KiB and 5.2 s, the duration read from the file headers (anything unreadable or longer → 400 50035 on `attachment_id`). `name` 2-32 chars, `volume` 0..1 (default 1), `emoji_name` a unicode emoji (≤32 chars, no letters, digits or spaces); `emoji_id` must be `null` until Vokko has custom emoji. Managing: create needs CREATE_GUILD_EXPRESSIONS or MANAGE_GUILD_EXPRESSIONS; edit/delete need MANAGE_GUILD_EXPRESSIONS, or CREATE_GUILD_EXPRESSIONS on your own upload. Files are claimed like sticker images, so deleting the channel they were uploaded in does not delete them. 48 per guild → 400 30045. Unknown sound → 404 10097. READY/GUILD_CREATE guild objects carry `soundboard_sounds`; changes arrive as GUILD_SOUNDBOARD_SOUND_CREATE/UPDATE (the sound, with `guild_id`) and GUILD_SOUNDBOARD_SOUND_DELETE `{sound_id, guild_id}` to the guild's members. Deleting a guild deletes its sounds.
- **Default sounds** have fixed small ids (1, 2, ...) and are generated by the server (synthesized tones, docs/assets-credits.md); their files are public (`GET /soundboard-default-sounds/{id}/file`, no auth).
- **Playing** (`POST /channels/{id}/send-soundboard-sound`): the channel must be a guild voice channel (else 400 50024) the caller is connected to (else 403 50013), not self-deafened or suppressed (403 50013); the caller needs USE_SOUNDBOARD and SPEAK there (403 50013). `source_guild_id` absent: a default sound, else a sound of the channel's guild. A sound of another guild needs USE_EXTERNAL_SOUNDS in the channel and the caller to be a member of that guild (else unknown, 404 10097); there is no Nitro gate. One play per user every 3 s per channel → 429 `RateLimitError` + `Retry-After`. The server sends VOICE_CHANNEL_EFFECT_SEND `{channel_id, guild_id, user_id, sound_id, sound_volume, emoji, source_guild_id, sound_url}` to the users connected to that voice channel only (sender included). No audio passes through LiveKit: every client plays the file locally at `sound_volume` × its own soundboard volume.
- **Entrance sounds.** `PUT /users/@me/entrance-sounds` sets the sound of one scope (`guild_id`, or `null` = global); the same rules decide which sounds may be picked (a default sound, or a sound of a guild the user is in). When the user joins a guild voice channel (a new binding or a move, not a mute toggle or a reconnect), the server resolves the guild's entrance sound, else the global one, and sends VOICE_CHANNEL_EFFECT_SEND with `entrance: true` to everyone in the channel, the joiner included, provided the joiner has USE_SOUNDBOARD and SPEAK there (and USE_EXTERNAL_SOUNDS for another guild's sound) and the sound still exists; otherwise nothing plays. At most one entrance sound per user and channel every 3 s; extra joins are silent. Leaving a guild drops its scope; a sound that is deleted simply stops playing.

Non-Discord error codes: none (10097 and 30045 are Discord's own).

## User settings

Synced preferences live on the account so they follow the user across devices; device-only ones never leave the client. The device-only list is `DEVICE_LOCAL` in `apps/desktop/src/ui/settingsSync.ts`: audio/video devices and volumes, voice processing (noise suppression and its kind, echo cancellation, gain, input profile, sensitivity), camera, camera background (uploads live in the device's IndexedDB), Go Live and viewer quality, stream attenuation and previews, debug logging, and the Accessibility display prefs (font size, zoom, saturation, contrast, motion and the rest), app icon, window and hardware acceleration.
- `disabled_sounds` is one list for the message sounds (`message`, `mention`) and the voice sounds of Voice & Video (`apps/desktop/src/notify/soundCatalog.ts`); the server checks the shape only (distinct strings), and a client drops ids it does not know.
- The blob is a flat JSON object of allow-listed keys (`vokko_protocol::api::user_settings::KEYS`, mirrored by the client registry in `apps/desktop/src/ui/settingsSync.ts`); keys are the snake_case form of the client pref name. Each key has a value kind (bool, enum, bounded int, short text, string list, keybind list); an unknown key or a wrong value → 400 50035 with `errors.<key>`, and nothing is saved. The stored blob is at most 64 KiB serialized (400 50035 on `settings`).
- `PATCH` merges: keys in `settings` are set, `null` removes a key (client default again), absent keys stay. It must carry the `version` it is based on; if that is not the current version → 409 with `UserSettingsConflict` (`code` 40090 plus the current `version` and `settings`). An accepted PATCH increments `version` even if nothing changed and sends `USER_SETTINGS_UPDATE` (the full `UserSettings`) to every gateway session of the user, the saving one included.
- Client conflict rule: server wins for keys another device changed since our base; our own pending keys the server did not touch are re-applied on top of the new blob and pushed again.
- Client accounts and devices: the local cache remembers the account it was last synced with (`localStorage["vokko.prefs.syncedFor"]`). A device that never synced uploads its non-default values for the keys the account has not set (the account keeps the keys it has); a device last synced with another account takes the new account's blob (or the defaults) and uploads nothing. Unsent changes are kept per account (`vokko.prefs.pending.<user id>`, values plus the version they were made on) and pushed on the next start unless another device changed the same key since; network errors, 429 and 5xx are retried after 5 s, 30 s, then every 120 s.
- Server-enforced privacy keys (defaults when absent): `dms_from_server_members` (true): together with the per-guild privacy above it decides who may DM you, Discord's rule: a friend always may; anyone else needs this key on and a shared guild whose `direct_messages` you have not turned off. It is checked when a 1:1 DM is opened, on every message sent and typing indicator in one, and when a 1:1 call is started or rung (403 50007; a refused call start is VOICE_CONNECT_FAILED `blocked`). Reopening an existing DM still returns it, joining a call the other side started and editing earlier messages stay allowed, and group DMs are not affected; `friend_requests_everyone` (true), `friend_requests_mutual_friends` (true), `friend_requests_mutual_guilds` (true): a friend request is accepted only from a source that one of the enabled keys allows (everyone, someone with a mutual friend, someone in a shared guild), else 403 80000 "Incoming friend requests disabled". `message_requests` is client-side: DMs from people who are not friends are filed under message requests and do not notify.
- `GET /users/@me/export` returns the caller's profile, settings, relationships, guild memberships, channels they wrote in or have open DMs with, and up to 20000 of their own messages (newest first, `messages_truncated` when cut). One export per user per 24 h, counted from the last successful export.

## Threads, forums and announcements

Channel types: 5 announcement, 10 announcement thread, 11 public thread, 12 private thread, 13 stage (see Stage channels), 15 forum. Threads are never part of `GET /guilds/{id}/channels`, `Guild.channels` in READY/GUILD_CREATE or CHANNEL_* events; READY and GUILD_CREATE carry the caller's active threads in `threads` and everything else arrives as THREAD_* events. Types and bits are in types.ts; permissions use Discord's bit values (MANAGE_THREADS 1<<34, CREATE_PUBLIC_THREADS 1<<35, CREATE_PRIVATE_THREADS 1<<36, SEND_MESSAGES_IN_THREADS 1<<38).

- **Thread = channel.** Messages, reactions, pins, typing, acks and search use the thread id as `channel_id`. `parent_id` is the text/announcement/forum channel, `owner_id` the creator, `message_count` the messages sent after the starter, `member_count` the joined members, `last_message_id` the latest message. A thread started from a message (or a forum post) has the **same id as its starter message**, which makes "one thread per message" a plain conflict (400 160004) and lets clients find the thread of a message without a lookup (`Message.thread` is also filled).
- **Starter messages.** Forum post: the first message is the real message (type 0, id == thread id, lives in the thread). From a message: the server inserts a type 21 `ThreadStarterMessage` as the first message of the thread, `message_reference` = the original (its channel_id is the parent), `referenced_message` filled. Without a message (text/announcement channel, public thread): a type 18 `ThreadCreated` system message is posted in the parent (content = thread name, `message_reference.channel_id` = thread id); private threads post none.
- **Permissions in a thread** are the parent's resolved permissions with SEND_MESSAGES replaced by SEND_MESSAGES_IN_THREADS. Public threads are visible to everyone who can view the parent; a private thread only to its members and holders of MANAGE_THREADS (403 50001 otherwise). Locked: only MANAGE_THREADS can send, unarchive or edit (403 160005 `Thread is locked`). Sending a message into an archived, unlocked thread unarchives it (the sender must be allowed to send); editing/reacting in an archived thread → 403 50083.
- **Auto-archive.** `auto_archive_duration` is one of 60, 1440, 4320, 10080 minutes (default: the parent's `default_auto_archive_duration`, else 1440). A thread with no message for that long is archived by a background sweep (every minute, `threads::sweep_archived`) with a THREAD_UPDATE; `archive_timestamp` is when `archived` last changed. Archived threads stay readable; joining or adding members to one → 403 50083 until it is unarchived.
- **Edit** (`PATCH /channels/{thread}`): name, `archived`, `auto_archive_duration`, `invitable`, `applied_tags` by the owner or MANAGE_THREADS; `locked` and `flags` (PINNED, forum posts only) need MANAGE_THREADS. Unarchiving an archived thread is the same PATCH with `archived: false`. Emits THREAD_UPDATE. Deleting the parent channel deletes its threads (THREAD_DELETE each, then CHANNEL_DELETE).
- **Creating a thread** adds the creator as a member. Sending a message in a thread joins the sender as a member; mentioning someone does not add them.
- **Forums.** `Channel.available_tags` (max 20, name 1-20 chars, ids are snowflakes assigned by the server), `default_reaction_emoji`, `default_sort_order` (0 latest activity, 1 creation date), `default_forum_layout` (1 list, 2 gallery), flag REQUIRE_TAG (1<<4). A post is a public thread (type 11) whose parent is the forum; `applied_tags` max 5, tags must belong to the forum, `moderated` tags only by MANAGE_THREADS. Removing a tag from the forum removes it from posts (THREAD_UPDATE per post). Only posts can exist in a forum: `POST /channels/{forum}/messages` → 400 50024. Search/sort/tag filter: `GET /channels/{forum}/threads/search`; `tag_setting` `match_some` (any tag) or `match_all`; `sort_by=last_message_time` orders by `last_message_id`.
- **Announcements.** A type 5 channel behaves like text. *Follow*: the caller follows the channel into a channel of their own (MANAGE_WEBHOOKS there; Vokko has no webhooks, the permission bit gates this). *Publish* (crosspost): the server copies the message into every follower channel as a regular message by the **original author** (no webhook identity) with `flags` IS_CROSSPOST and `message_reference` = the source message (channel and guild of the source); embeds and content are copied, **attachments are not forwarded** in this version. The source message gets `flags` CROSSPOSTED and a MESSAGE_UPDATE. Deleting the source or the follow target removes the follow; deleting a copy does not affect the source.
- **Gateway.** THREAD_CREATE (public: everyone who can view the parent; private: the members; also sent to a user who is added to a private thread), THREAD_UPDATE (same audience), THREAD_DELETE `{id, guild_id, parent_id, type}`, THREAD_MEMBER_UPDATE (to the user who joined), THREAD_MEMBERS_UPDATE `{id, guild_id, member_count, added_members?, removed_member_ids?}` (to everyone who can see the thread). MESSAGE_*, TYPING_START, reaction and ack events for a thread go to its viewers only. No THREAD_LIST_SYNC: a client refetches `GET /guilds/{id}/threads/active` after a permission change.
- Errors: 50024 wrong channel type, 50083 thread archived, 160004 thread already exists for the message, 160005 thread locked, 220003 forum tag required, 10065 unknown thread member, 40033 message already published.

## Apps: bots, slash commands, interactions, webhooks

Applications own a bot user (`User.bot = true`, user id == application id). Shapes: the "Applications, bots, slash commands" block of types.ts.

**Auth.** `Authorization: Bot <token>` authenticates as the bot in gateway `op 2 Identify {token: "Bot <token>"}` (a bad bot token closes 4004 like a bad session token) and on the REST routes listed for bots; every other route answers a bot token 403 20001 "Bots cannot use this endpoint". Bot tokens are random, stored as SHA-256, shown once (create and reset). A webhook or interaction token is never an `Authorization` value: it only works inside its own `/webhooks/{id}/{token}` URLs.

**Bot routes** (an allowlist in `crates/server/src/bot_routes.rs`; a new route stays closed to bots until it is listed): `GET/PATCH /users/@me`, `GET /users/@me/guilds`, `DELETE /users/@me/guilds/{id}`, `POST /users/@me/channels`, `GET /users/{id}`; guild, channel, member, ban, role, onboarding, scheduled event, sticker, thread, pin, reaction, typing, invite-create, follower, overwrite, attachment upload and webhook management routes (each still needs the permission a person would need); `GET /invites/{code}`; `/applications/{id}/commands*` and `/applications/{id}/guilds/{gid}/commands*`; `/interactions/{id}/{token}/callback`; `/webhooks/{id}*`. Not for bots: `/auth/*`, account, sessions, MFA, OAuth links, relationships, accepting invites, creating or deleting guilds, `/applications`, `/oauth2/*`, `POST /interactions`, search, bookmarks, reminders, read states, GIFs, settings. Bots open one-to-one DMs only with users they share a guild with (403 50007 otherwise, no group DMs), and lose access to a DM once they no longer share a guild with the other recipient (403 50001).

Per app and scope: 100 CHAT_INPUT, 5 USER, 5 MESSAGE (400 30032). Name + type is unique per app and scope. Invalid bodies → 400 50035 with `errors` naming the field. Command writes for one application are serialised and a bulk overwrite is all or nothing.

**Interactions.** `POST /interactions` creates the interaction and sends INTERACTION_CREATE (`Interaction`, `resolved` filled for user/channel/role options and the target) to the bot's sessions. The bot answers `POST /interactions/{id}/{token}/callback`:
- type 4: creates the response message (type 20 for CHAT_INPUT, 23 for USER/MESSAGE) authored by the bot user, `application_id` and `webhook_id` = application id, `interaction_metadata` = who ran which command. Not limited by the bot's channel permissions (Discord's webhook semantics), except `@everyone`/`@here`: they ping only when `allowed_mentions.parse` lists `everyone` and the bot has MENTION_EVERYONE in the channel (also for followups and edits). If storing the response fails, the interaction is not counted as answered.
- type 5: same message with `content: ""` and `flags` Loading; the bot fills it with `PATCH /webhooks/{app_id}/{token}/messages/@original` (MESSAGE_UPDATE, Loading cleared).
- type 8 (autocomplete interactions only): `choices` go to the invoking user as APPLICATION_COMMAND_AUTOCOMPLETE_RESPONSE.
- No callback within 3 s → INTERACTION_FAILURE to the invoking user ("The application did not respond") and the token stops accepting callbacks. Followups and @original edits work for 15 minutes from creation, then 404 10062.
- `flags: 64` (Ephemeral) on the callback or a followup: the message exists only for the invoking user. It is stored separately (never in the channel history of anyone else, never in search, pins, counts, read states or `last_message_id`), MESSAGE_CREATE/UPDATE/DELETE go only to the invoking user's sessions, and `GET /channels/{id}/messages` returns it only to that user. The user dismisses it with `DELETE /channels/{id}/messages/{mid}` (204, MESSAGE_DELETE to their sessions); nobody else can see, edit, react to, reply to or pin it (404 10008). Ephemeral messages are deleted after 24 h.

**Webhooks.** Incoming webhooks (type 1) are created per channel (text/announcement channels and threads' parents; forum channels → 400 50024). The token (68 random hex chars) and the execute URL `<public_url>/api/v1/webhooks/{id}/{token}` are shown to MANAGE_WEBHOOKS holders. Webhook messages behave like normal messages for everyone (history, search, pins, reactions, deletes by MANAGE_MESSAGES) except that only the webhook (token routes) can edit them. Mentions in executed content ping like a user message; `@everyone` only when `allowed_mentions` allows it.

**Embeds** from bots and webhooks (execute, callbacks, followups, edits): at most 10, always stored as `type: "rich"`; title ≤256, description ≤4096, ≤25 fields (name ≤256, value ≤1024), footer text ≤2048, author name ≤256, and ≤6000 characters across all embeds of the message (400 50035 naming the field). URLs (`url`, `image`/`thumbnail`/`video.url`, `author.url`/`icon_url`, `footer.icon_url`, `provider.url`) must be http(s) and ≤2048 characters; others are dropped (a media part with a bad URL is dropped whole). WEBHOOKS_UPDATE `{guild_id, channel_id}` goes to members with MANAGE_WEBHOOKS in that channel; clients refetch. Deleting a channel deletes its webhooks.

Errors: 10002 unknown application, 10015 unknown webhook, 10062 unknown interaction, 10063 unknown application command, 20001 bots cannot use this endpoint, 30005 max roles, 30007 max webhooks, 30032 max application commands, 30035 max applications, 40060 interaction already acknowledged, 50027 invalid webhook token.

**Gateway.** INTERACTION_CREATE (bot only), INTERACTION_FAILURE and APPLICATION_COMMAND_AUTOCOMPLETE_RESPONSE (invoking user's sessions only), WEBHOOKS_UPDATE. Message events for ephemeral messages only reach the invoking user.

## Custom emoji

Discord behaviour with every Nitro emoji perk free: a member can use the emoji of **any guild they are in, anywhere** (other guilds, DMs, reactions), animated emoji included. Message content references them as `<:name:id>` / `<a:name:id>` (the server does not rewrite or validate content; clients render the image from `GET /emojis/{id}`, which works for viewers outside the emoji's guild too).

- **Upload**: the image is first uploaded with `POST /channels/{id}/attachments` (any channel the caller can attach to), then `POST /guilds/{id}/emojis {name, image_attachment_id, roles?}` claims it (the caller's own pending, unclaimed upload; once claimed it cannot be reused as an avatar, banner, icon, sticker or another emoji). PNG, GIF or WebP only, at most 256 KiB, otherwise 400 50035 on `image_attachment_id`. `animated` = GIF or animated WebP (VP8X animation flag).
- **Name**: 2-32 characters of `A-Z a-z 0-9 _` (400 50035 on `name`). Names need not be unique (Discord allows duplicates).
- **Limits**: 250 static + 250 animated emoji per guild (Discord's top boost tier, free in Vokko) → 400 30008 "Maximum number of emojis reached".
- **Permissions**: create/edit/delete need MANAGE_GUILD_EXPRESSIONS (1<<30, 403 50013); list/get need guild membership (403 50001). `roles` must be roles of the guild other than @everyone (400 50035); an emoji with roles is usable only by members holding one of them.
- **Reactions** with a custom emoji (`name:id`, the id decides; the stored name is used): unknown emoji → 400 10014 "Unknown Emoji"; the reactor must be a member of the emoji's guild and, for a role-restricted emoji, hold one of its roles, and an emoji of another guild in a guild channel needs USE_EXTERNAL_EMOJIS there (default on for @everyone; DMs never need it) → 403 50013. Removing a reaction and listing reactors never check the emoji (a deleted emoji's reactions stay, with `id` and `name`). Reaction objects and MESSAGE_REACTION_ADD/REMOVE carry `emoji.animated` for custom emoji whose guild still has them.
- **Delete** removes the emoji and its stored file; `GET /emojis/{id}` then answers 404 and clients fall back to `:name:`.
- **Gateway**: READY guilds and GUILD_CREATE carry `emojis` (no `user`; omitted when empty). Every create/edit/delete sends GUILD_EMOJIS_UPDATE `{guild_id, emojis}` (the full list) to every member of the guild.

## Polls

A poll is a message with `poll` (Discord's shape: `Poll`, `PollCreateRequest`, `PollVoteEvent` in types.ts). Created with `CreateMessageRequest.poll`:
question 1-300 characters, 1-10 answers of 1-55 characters each with an optional emoji, `duration` 1-768 hours (default 24; the client offers
1 h, 4 h, 8 h, 24 h, 3 d, 1 w, 2 w), `allow_multiselect` default false, `layout_type` 1. `content` is optional next to a poll; attachments are not allowed
(400 50035). Guild channels need SEND_MESSAGES and SEND_POLLS (1<<49, part of the default @everyone set); DMs and group DMs need nothing extra.
Forum channels take no messages, so no polls (50024).

- **Results** are computed live: `results.answer_counts` has one entry per answer (zero counts included) and `me_voted` is per viewer (REST and
  each receiver of MESSAGE_CREATE/UPDATE). `is_finalized` turns true once the poll has ended and its result message exists.
- **Voting** (`PUT .../answers/{answer_id}/@me`) needs VIEW_CHANNEL + READ_MESSAGE_HISTORY. Single choice: voting for another answer moves the vote
  (MESSAGE_POLL_VOTE_REMOVE for the old answer, then MESSAGE_POLL_VOTE_ADD). Multiselect: each answer is a separate vote. Repeating a vote, or removing
  one that does not exist, is a 204 with no event. Unknown answer → 400 50035. At or after `expiry` → 400 520001 `Poll expired`. Archived thread → 403
  50083. Removing a vote follows the same rules. Events go to everyone who can see the channel.
- **Voters** (`GET .../answers/{answer_id}`): users ordered by id, `after` = user id, `limit` 1-100 (default 25).
- Votes and voters on a message without a poll → 404 10008. A forum post's first message cannot carry a poll (`poll` is ignored there), and
  publishing (crosspost) a poll message copies its content only, not the poll. A poll message cannot carry stickers or be a forward
  (`poll` with `sticker_ids` or a forward `message_reference` → 400 50035), and a poll message cannot be forwarded (400 50035 on `message_reference`).
- **Ending.** `POST .../expire` (the poll's author only, 403 50005 otherwise; a non-poll message → 400 520006; an ended poll → 400 520001) sets
  `expiry` to now and finalises at once. A background sweep (every 5 s, `polls::sweep_expired`) finalises polls whose expiry has passed. Finalising
  happens exactly once per poll (a conditional UPDATE decides the winner of a race between the sweep and End Poll Now): it emits MESSAGE_UPDATE for the
  poll message and posts a type 46 `PollResult` message (author = the poll's author, `message_reference` = the poll message, content empty, no pings)
  whose single embed has `type: "poll_result"` and Discord's `fields`: `poll_question_text`, `total_votes`, and when one answer has strictly the most
  votes `victor_answer_id`, `victor_answer_text`, `victor_answer_votes`, `victor_answer_emoji_id`, `victor_answer_emoji_name` (values are strings).
  A vote either commits before the poll is finalised (and is counted) or is refused with 520001; counts never change after finalising.
- **Editing** a poll message → 400 520003 `Cannot edit a poll message`. Deleting it deletes the poll and its votes (no result message).

## Server admin: hierarchy, prune, audit log, safety

- **Hierarchy.** Roles rank by `position` (ties: older snowflake higher), @everyone always last. Everyone but the owner can only edit, delete, assign, remove or move roles strictly below their own highest role, and only move them to positions below it; role edits can only flip permission bits the actor holds. The owner bypasses all of it. Violations → 403 50013.
- **Role icon.** `Role.unicode_emoji` (any emoji, 1-32 chars), free for every server; image role icons are not supported yet.
- **Prune.** A member is inactive when they joined more than `days` days ago and posted no message of their own (join notices do not count) in the guild during the last `days` days. Never the owner or the caller; members with roles only when every role they hold is in `include_roles` (each of which must be below the caller's highest role, 403 50013 otherwise). `days` 1-30 (400 50035).
- **Audit log.** Entries are recorded for guild updates (1), channel create/update/delete (10-12), overwrite create/update/delete (13-15, options `id`, `type`, `role_name`), kick (20), prune (21, options `delete_member_days`, `members_removed`), ban add/remove (22/23), member nick/timeout (24), member role add/remove (25, `$add` / `$remove` changes with `[{id, name}]`), role create/update/delete (30-32), invite create / delete (40/42, in routes/invites.rs), a message deleted by someone other than its author (72, options `channel_id`, `count`), pin/unpin (74/75, options `channel_id`, `message_id`), AutoMod rule create/update/delete (140-142), report close/reopen (250, Vokko-only, see Reports) and AutoMod blocks (143, the author is `user_id` and `target_id`, options `channel_id`, `auto_moderation_rule_name`, `auto_moderation_rule_trigger_type`). Webhooks, emoji, stickers, scheduled events and onboarding have no routes in this version; their numbers are reserved in `AuditLogEvent` and `audit::record` is the hook. `reason` comes from the `X-Audit-Log-Reason` request header (percent-decoded, trimmed, cut to 512 characters; CORS allows it); a ban stores the body `reason` and falls back to the header. `changes` lists only keys that changed. `before` / `after` page by entry id. Entries are kept indefinitely (no 90-day expiry yet). `GUILD_AUDIT_LOG_ENTRY_CREATE` (the entry) goes only to members with VIEW_AUDIT_LOG (owner and administrators included).
- **Safety.** `verification_level` is enforced when sending a message in a guild channel (members with any role, administrators and the owner bypass it): Medium = account older than 5 minutes, High / VeryHigh = also a member for more than 10 minutes; otherwise 403 50009 "Channel verification level is too high for you to gain access". Low counts every account as verified (no email verification exists). `explicit_content_filter` is stored and shown; media is not scanned yet.
- **AutoMod** (keyword rules only: `trigger_type` 1, `event_type` 1, action 1 BLOCK_MESSAGE; anything else → 400 50035). At most 6 keyword rules per guild (400 30035). `keyword_filter` ≤1000 entries of 1-60 chars, `allow_list` ≤100, `exempt_roles` ≤20 (roles of the guild), `exempt_channels` ≤50 (channels of the guild), `name` 1-100. Matching is case-insensitive on whole words: `cat` matches the word cat, `cat*` words starting with cat, `*cat` words ending with it, `*cat*` anywhere; a keyword may contain spaces. A word matched by `allow_list` never triggers. Checked on message create and on content edits (messages, thread and forum post starters) for enabled rules; exempt: the owner, members with MANAGE_GUILD or ADMINISTRATOR, members holding an exempt role, and exempt channels (a thread uses its parent). A blocked message is not stored: 400 code 200000 "Message was blocked by automatic moderation" (`errors.content._errors[0].message` = the custom message when set) plus an audit entry 143. AUTO_MODERATION_RULE_* go to members with MANAGE_GUILD.
- Errors: 50009 verification level, 200000 AutoMod block, 10066 unknown AutoMod rule, 30035 too many AutoMod rules.

## Reports (MOD-009)

Discord sends reports to its own Trust & Safety team through an undocumented API. Vokko has no central team, so a report goes to the guild's moderators: members with MANAGE_MESSAGES or MODERATE_MEMBERS (administrators and the owner included; bot accounts never, 403 50013). A moderator never sees, or closes, a report about themselves (the owner neither: their reports go to the other moderators).

| Method | Path | Body → Response |
|---|---|---|
| POST | /channels/{id}/messages/{mid}/report | `CreateReportRequest` `{reason, details?}` → `Report`. Needs read access to the message (403 50001/50013 like reading it, unknown message 404 10008). Not your own message, not a system message (400 50035 `errors.message_id`). A DM message report has `guild_id: null` and is kept for the instance operator (no in-app queue; see self-hosting.md) |
| POST | /guilds/{id}/members/{uid}/report | `CreateReportRequest` → `Report`. Reporter must be a member (403 50001); target must be a current member (404 10007); not yourself (400 50035 `errors.user_id`) |
| GET | /guilds/{id}/reports?status&before&limit | `Report[]` newest first (moderators only, else 403 50013). `status` `open` (default), `resolved`, `dismissed` or `all`; `limit` 1-100 (default 50); next page: `before` = last id. Left out: reports about the caller, message reports from channels the caller cannot read (VIEW_CHANNEL and READ_MESSAGE_HISTORY), and message reports from deleted channels unless the caller is an administrator (the channel may have been private) |
| PATCH | /guilds/{id}/reports/{report_id} | `UpdateReportRequest` `{status}` → `Report` (moderators; a report they cannot see is 404). `resolved`/`dismissed` set `closed_by` and `closed_at`, `open` clears them; reopening while the reporter has a newer open report of the same target is 400 50035 |

- `reason`: `spam`, `harassment`, `hate`, `sexual`, `violence`, `self_harm`, `impersonation`, `other`. `details`: optional, trimmed, at most 1000 characters (blank is `null`).
- `Report`: `{id, guild_id, target_type: "message" | "user", reporter: User, target_user: User, channel_id, message_id, message_content, reason, details, status, created_at, closed_by, closed_at}`. `message_content` is the text when it was reported (edits and deletion do not change it). The reporter is shown to moderators.
- One open report per reporter and target: reporting the same message (or member of that guild) again returns the open report unchanged, also with a different reason.
- Rate limit per reporter: 5 new reports, then 1 per minute (429 `RateLimitError`); repeating an open report does not count. At most 50 open reports per reporter in a guild and 20 for DM messages (400 30093).
- Closing or reopening records audit entry 250 (`ReportUpdate`, Vokko-only): `target_id` is the report id, the one change is `status` (old to new), `reason` comes from `X-Audit-Log-Reason`. The reporter, the target and the reason for the report are left out, since VIEW_AUDIT_LOG members need not be moderators. Setting the status a report already has records nothing.
- No gateway event yet: moderators load the list.

## Apply to Join (join requests, Server Settings > Access)

Discord's member verification form and guild join requests. A guild's `join_mode` (also on `Invite.guild`) is `0` Invite Only (default) or `1` Apply to Join; MANAGE_GUILD switches it through PATCH /guilds/{id} `{join_mode}` (other values → 400 50035), audit key `join_mode`.

**Every way in is gated.** While `join_mode` is 1, nobody becomes a member without an approved request: POST /invites/{code} by a non-member → 403 code 150009 "This server requires an application to join" (members keep working: no change), temporary invites included; approval is the only path. Exceptions, both actions of a server manager: the owner at creation, and a bot added through OAuth2 authorize by a MANAGE_GUILD member (Discord lets bots in the same way).

Shapes:
- `MemberVerificationForm { description: string | null, form_fields: MemberVerificationField[] }`; `MemberVerificationField { field_type: "TERMS" | "TEXT_INPUT" | "PARAGRAPH" | "MULTIPLE_CHOICE", label: string, required: boolean, values?: string[] | null, description?: string | null, placeholder?: string | null, response?: boolean | number | string | null }`. `values` are the rules (TERMS, 1-16 entries of 1-300 chars) or the choices (MULTIPLE_CHOICE, 1-8 of 1-150); TEXT_INPUT and PARAGRAPH have none. At most one TERMS field and 5 others; `label` 1-300, `description` up to 300 (form) / 300 (field), `placeholder` up to 100. `response`: TERMS `true`; TEXT_INPUT a string up to 150 chars, PARAGRAPH up to 1000; MULTIPLE_CHOICE the index of the choice. A required field needs a (non-blank) response.
- `GuildJoinRequest { id, guild_id, user_id, user: User, created_at, application_status: "SUBMITTED" | "APPROVED" | "REJECTED", form_responses: MemberVerificationField[], rejection_reason: string | null, actioned_at: string | null, actioned_by_user: User | null }`. One request per user and guild.

| Method | Path | Notes |
|---|---|---|
| GET | /guilds/{id}/member-verification?invite_code= | `MemberVerificationForm`; members may read it, a non-member needs `invite_code` of a live invite to this guild (else 404 10004, so it does not reveal the guild). A guild with no form returns `{description: null, form_fields: []}` |

Audit `MEMBER_UPDATE`-style entries are not written (Discord shows these in the requests list instead) |

Gateway `GUILD_JOIN_REQUEST_CREATE` / `GUILD_JOIN_REQUEST_UPDATE` `{guild_id, status, request}` and `GUILD_JOIN_REQUEST_DELETE` `{guild_id, id, user_id}` go to the applicant and to members with KICK_MEMBERS or MANAGE_GUILD. The applicant's copies (events, `GET`/`PUT` `@me`) have `actioned_by_user` null. Banning a user deletes their request (DELETE event); deleting the guild deletes all of them. Applicants see nothing of the guild beyond the invite preview and the form until approved.

## Gateway

`GET /gateway` (at the server root, not under `/api/v1`; e.g. `ws://127.0.0.1:8710/gateway`) upgrades to WebSocket. Text frames carrying `GatewayPayload`.

1. Server sends `op 10 Hello {heartbeat_interval: 41250}`.
2. Client sends `op 2 Identify {token}`. Bad token → close code 4004.
3. Server dispatches `READY` (op 0, `s` increments per dispatch).
4. Client sends `op 1 Heartbeat {d: last_seq}` every interval; server replies `op 11`. Missing two heartbeats → server closes 4009.
5. `op 4 VoiceStateUpdate {guild_id, channel_id, self_mute, self_deaf, self_video}` joins, moves, leaves (`channel_id: null`) or toggles self mute/deafen (see Voice).
6. `op 6 Resume {token, session_id, seq}` replays missed dispatches if the session buffer still has them; otherwise `op 9 InvalidSession`, and the client re-identifies.

Events are delivered only to users who can see the channel/guild. Event names and payloads: `GatewayEvents` in types.ts. Presence: connected → online, last connection closed → offline; `op 3 {status, custom_status, activities?}` updates it (custom_status max 128 chars; `activities` below). The presence preference is not kept across a full disconnect.

Poll events: `MESSAGE_POLL_VOTE_ADD` / `MESSAGE_POLL_VOTE_REMOVE` `{user_id, channel_id, message_id, guild_id, answer_id}` to the channel's viewers;
clients apply them to `results` (and `me_voted` when `user_id` is theirs).

**TTS.** `CreateMessageRequest.tts` (optional bool, default false) and `Message.tts` (always serialized, false by default). A message is stored with `tts` true only when the sender holds SEND_TTS_MESSAGES (1 << 12) in the channel; without it the send still succeeds (200) and the message is stored and returned with `tts: false`, like Discord (no error). `@everyone` does not hold SEND_TTS_MESSAGES by default (Discord's new-guild default is not documented, so it is left off); DMs grant it, as on Discord (so a bot's `app_permissions` in a DM interaction includes it too). Webhook, interaction and system messages are always `tts: false`. The client speaks a received tts message only while its channel is open, for other authors, and when the playback preference is on.

Semantics notes: a reply puts the replied-to author in `mentions` (Discord default). Pinning emits MESSAGE_UPDATE for the pinned message plus a type 6 system message (MESSAGE_CREATE). `referenced_message.reactions` is always `[]`. Role mentions only drive `mention_count` (no `mention_roles` field).

Message search (`MessageSearchQuery`): Discord's query shape. Array filters use repeated keys (`?has=image&has=link`, `?author_id=1&author_id=2`; values inside one filter are OR, different filters are AND, except repeated `has` which is AND). `content`: words, case-insensitive, all must appear (`simple` Postgres text search, so Swedish and English both work with no stemming); `"quoted phrase"` and `-excluded` follow `websearch_to_tsquery`. `author_id` (users), `mentions` (users, includes reply targets), `channel_id` (guild route only; channels the caller cannot read are ignored), `has` = `link | embed | file | image | video | sound | sticker` (`file` = any attachment; `image`/`video`/`sound` by attachment content type or embed type; `sticker` = the message has sticker items), `pinned` (`true` only pinned, `false` only unpinned, absent both), `min_id` / `max_id` (exclusive snowflakes: Discord's after/before/during are computed client-side from the date), `offset` (0-9975, default 0), `limit` (1-25, default 25), `sort_by` (`timestamp` default | `relevance`), `sort_order` (`desc` default | `asc`). Out-of-range values → 400 50035. `relevance` without `content` falls back to timestamp. Only user messages are searched (types 0 and 19): pin notices and join messages never match, so `from:` alone lists real messages. Response `{total_results, messages: Message[][]}`: `total_results` counts every match in the readable set (before offset/limit) and never includes channels the caller cannot read; each hit is a one-element array (Discord's shape, no context messages), with `Reaction.me` filled for the caller.

Read states: READY includes a read state for every channel the user can see that has messages. When a user joins a guild or a DM is created, their read state starts at the channel's latest message (nothing is unread). A channel without a read state counts as unread on the client.

## Adopted from Discord client facts (docs/research/discord-client-facts.md)
We match Discord's user-visible behaviour, not its wire protocol byte for byte. Adopted: `allowed_mentions` on send (reply ping toggle), paginated pins with `pinned_at` and the 250-pin cap, 10 files per message (25 MiB per file, configurable), bulk ack, 429 responses with `RateLimitError` + `Retry-After` header (code 20016 for slowmode later).
Client gateway behaviour (shell): first heartbeat after `random() * interval`, then every interval; no ACK before the next beat → close and reconnect; Hello must arrive within 30 s; resume only if the last ACK is under 3 minutes old, else identify; reconnect backoff 1 s doubling to 60 s with jitter; stop reconnecting only on close 4004 (bad token); the client closes its own sockets with 4000.
Not adopted for now: op 40 QoS heartbeat, ETF encoding, zstd/zlib compression, capabilities/client_state in Identify, the cloud upload flow (resumable PUT to an upload URL), ack tokens.

Embeds: on message create/edit the server extracts up to 5 http(s) URLs (not inside code, not `<url>`-wrapped), fetches each with a 5 s timeout, 1 MiB cap, no private/loopback addresses (SSRF guard), and parses Open Graph / Twitter card / oEmbed-less HTML meta into `Embed` (type link/article/image/video). Results arrive via MESSAGE_UPDATE after the create. Editing with flags SUPPRESS_EMBEDS (1<<2) clears them. Invite links are rendered client-side from GET /invites/{code}, not unfurled.

Moderation: missing permission → 403 50013; acting on someone at or above your highest role (or the owner) → 403 50013. Role/role-position edits are limited to roles below the actor's highest role (owner exempt). Channel overwrites resolve in Discord's order (@everyone, roles combined, member); ADMINISTRATOR in an overwrite is ignored. On guild join the server posts a UserJoin (type 7) system message in `system_channel_id` when set. A member timeout survives leaving or being kicked and is restored on rejoin (a ban drops it). Overwrite PUT/DELETE and `lock_permissions` require MANAGE_ROLES in the channel and every permission bit the change flips (403 50013); a caller who cannot see the channel gets 403 50001. A user can neither kick, ban nor time out themselves or the owner (403 50013). Bodies of `PUT /bans/{uid}` and `POST /roles` must be present (send `{}`).

Further semantics: `embed.url` is the normalised parsed URL; `proxy_url` is never set (clients load og:image/video straight from the origin; CSP + IP-exposure trade-off, revisit with a media proxy). Only the author may set message flags. Unfurling has no cache. A block closes 1:1 DMs both ways (403 50007) and DELETE never lifts the other side's block. Presence (READY and PRESENCE_UPDATE) is shared only with guild members, accepted friends and peers of DMs open on both sides. A closed DM is hidden for that user until a new message arrives. Pending (unreferenced) attachments are deleted after 1 h.

Presence on join: when a user joins a guild, existing members who didn't already share a guild/DM/relationship with them get GUILD_MEMBER_ADD followed by a PRESENCE_UPDATE with the joiner's current presence (if not offline). The joiner's GUILD_CREATE carries `presences` for the guild's online members. On leave/kick/ban, members who no longer share anything with the user get PRESENCE_UPDATE offline for them (and vice versa).

Presence status: `PresenceStatus` includes `invisible` (valid in op 3 and in the user's own READY presence; everyone else sees `offline`). The chosen status and custom_status are stored and restored on the user's first connection (default online); on the last disconnect others see offline but the choice is kept. Others never see a custom_status or an activity while the user is offline or invisible; the user's own READY and PRESENCE_UPDATE carry the chosen status (including `invisible`) and custom_status. `offline` sent in op 3 is stored as `invisible`. Activities: `Presence.activities` is `[{name, type: 0, timestamps?: {start}}]` (type 0 "Playing", `start` is unix ms, omitted when empty). Op 3 `activities` absent keeps the current list; `[]` withdraws what this session reported. Activities belong to the gateway session that reported them: with several sessions of one user (desktop app plus a browser tab) the list of the session that reported most recently is shown, and an empty list from another session never clears it; when the reporting connection closes its list goes with it (the previous session's list, if any, is shown again; the last disconnect clears everything), so a client re-sends its activity after every READY **and** RESUMED. Only a client that owns the activity (the desktop app, from game detection) should send the field; a browser sends status and custom_status only. Validation closes 4002 for: more than 1 entry, `type` other than 0, a name that is blank, over 128 Unicode code points (not UTF-16 units or bytes), or that contains a control character or an invisible one (zero-width, bidi marks and overrides, soft hyphen, fillers), and a negative `timestamps.start`. Two shapes are not a 4002 but a silently ignored op 3 (the whole update, status included, is dropped, as for any undecodable payload): a `type` outside 0 to 255 and a non-string `name`. The desktop app fills the list from game detection (`Share my activity` in Activity Privacy). Deleting a guild does not send presence clean-up (members reconnect or learn from the next update).

Category sync: a channel created with `parent_id` copies the category's overwrites. PATCH /channels/{id} takes `lock_permissions?: boolean` together with `parent_id` (true = copy the new parent's overwrites, false/absent = keep its own). PUT/DELETE of an overwrite on a category also applies to every child whose overwrites equalled the category's before the change (CHANNEL_UPDATE per child). Clients show "synced" by comparing the arrays.

Limits and abuse controls: uploads max 25 MiB per file (server setting `VOKKO_MAX_UPLOAD_MB`, deliberately moderate: Vokko gives Nitro perks free but not Nitro's 500 MiB), 10 files per message, pending uploads quota 100 MiB per user (413, code 40005). Attachment files are streamed with `Cache-Control: private`. Gateway: frames over 16 KiB end the connection; custom_status over 128 chars → close 4002; op 3 more than 5/min per session or Identify more than 10/min per user → close 4008; a slow reader (queue full or a write stalled 10 s) → close 1013 (resumable); no Identify within 30 s → dropped; more than 16 unidentified sockets per address → HTTP 429. Logout closes that token's sessions with 4004. REST rate limits are per user, and per client address on /auth/* (burst 10, then 1 per 2 s). A client address is an IPv4 address or an IPv6 /64 (for these limits and the unidentified-socket cap); signed-out /auth/* calls and invite previews from IPv6 also share a bucket per /48 of 16 times that budget. Behind a trusted proxy the address is the last entry of the last `X-Forwarded-For` header (one proxy hop). ack-bulk max 100 entries.

Profile perks (docs/research/discord-nitro-perks.md): every Discord Nitro profile perk is free. Animated avatars/banners are accepted as GIF/WebP with moderate caps (avatar ≤8 MiB in, 512x512 out, animated ≤2 MiB stored; banner ≤10 MiB in, ≤1360x480 out, animated ≤4 MiB stored). Decorations, profile effects and tag badges are ids into Vokko's own open asset set (shipped with the client), never Discord assets. Per-server member profile fields override the user's inside that guild; USER_UPDATE / GUILD_MEMBER_UPDATE carry the changes. Message length stays 2000 for now (the 4000 perk is a later decision with the composer). No boost levels: per-server limits are one owner-editable config block.

## Accounts

Registration (`RegisterRequest`): `email`, `username`, `password`, `date_of_birth` (`YYYY-MM-DD`, required) and `consent` (required `true` when `InstanceInfo.terms` is not null); `global_name` optional. Errors are 50035 with the field name: `username` 2-32 chars of `a-z 0-9 _ .`, no `..`, input is trimmed and lowercased, "Already taken."; `password` 8-128 chars and not too weak or common ("Password is too weak or common to use.", also when it contains the username or the email's local part); `date_of_birth` must be a real past date and the user at least `min_age` (`VOKKO_MIN_AGE`, default 13) years old; `consent` "You need to agree to the terms." The username check (`POST /auth/username-attempt`) never says why a name is taken.

Email links: `<VOKKO_WEB_URL>/verify#token=<t>` and `<VOKKO_WEB_URL>/reset#token=<t>` (default `VOKKO_PUBLIC_URL`). Tokens are 32 random bytes, stored as SHA-256, single use; verification links live 24 h, reset links 1 h. A new link of the same kind replaces the previous one.

Account editing (`PATCH /users/@me/account`, Discord puts this on `PATCH /users/@me`; Vokko keeps it separate so the profile route stays password-free): only sent keys change, all in one request. Wrong or missing current password → 50035 `password` "Password does not match.". `username` follows the registration rules and emits USER_UPDATE. `email` does not change the address yet: it becomes `pending_email`, a verification link goes to the new address and a notice to the old one; the switch happens when the link is used (`POST /auth/verify`), and a new request replaces the pending one. `new_password` follows the registration password rules and revokes every other session of the user (their gateways close with 4004); the calling token stays valid. An account without a password (OAuth-only) sets its first one with `new_password` alone.

Disable keeps everything but signs the user out everywhere; the next successful login clears it. Delete removes the user from every guild (GUILD_MEMBER_REMOVE), drops relationships (RELATIONSHIP_REMOVE to the others), sessions, tokens and linked sign-in methods, and rewrites the user row: username `deleted_user_<12 hex>`, display name "Deleted User", no avatar, banner, bio or other profile fields, email freed; USER_UPDATE carries that to everyone who shared something with them. Their messages and DMs stay and render with the anonymised author.

Two-factor (TOTP, RFC 6238: SHA-1, 6 digits, 30 s steps, ±1 step accepted, a step is never accepted twice): enabling needs the password, the client-made secret and a current code from it; the answer has 10 backup codes (8 chars `a-z 0-9`), stored as SHA-256 and single use. Login with two-factor on answers `{token: null, mfa: true, ticket, totp: true, backup: true}`; the client then posts the code to `/auth/mfa/totp`. Wrong codes → 400 50035 `code` "Invalid two-factor code"; an expired or used-up ticket → 400 50035 `ticket`. Disabling two-factor deletes the backup codes. Disable/delete account then also need `code`.

Sessions (`UserSession`): `id_hash` (opaque, stable per session), `approx_last_used_time` (updated at most every 5 minutes), `client_info.os` / `client_info.platform` parsed from the User-Agent at sign-in (e.g. "Windows" / "Chrome", "Vokko Desktop"), `current` for the calling token. No location is recorded.

Password reset: `/auth/forgot` never reveals whether an account exists and is rate limited per address like every `/auth/*` route. The link is `<VOKKO_WEB_URL>/reset#token=<t>`, valid 1 h, single use; a later password change or reset invalidates it.

Sign in with GitHub, Google and OpenID Connect (Vokko extension, Discord has no equivalent). A provider is offered only when its variables are set: `VOKKO_OAUTH_GITHUB_CLIENT_ID/SECRET` (GitHub OAuth app, id `github`), `VOKKO_OAUTH_GOOGLE_CLIENT_ID/SECRET` (Google OIDC, id `google`), `VOKKO_OIDC_<NAME>_ISSUER/CLIENT_ID/SECRET` (+ optional `_DISPLAY_NAME`; id `<name>` lowercased, e.g. GitLab, Microsoft, Keycloak, Authentik). The provider redirect URI to register is `<VOKKO_PUBLIC_URL>/api/v1/auth/oauth/<id>/callback`. Authorization code flow with PKCE (S256), `state` and (OIDC) `nonce`, all checked by the server, which also does the token exchange; client secrets and provider tokens never reach the client and are not stored. OIDC identities are the ID token's `sub`, GitHub's the numeric user id; the provider's email counts only when the provider says it is verified.

The client starts with `POST /auth/oauth/{id}/authorize {target, client_challenge}`: `client_challenge` is base64url(SHA-256(client_verifier)) of a random verifier the client keeps, so a result code that leaks (another app claiming `vokko://`, browser history) cannot be redeemed elsewhere. The browser goes to the provider, back to the server callback, then to the client with a single-use result code (10 minutes). `POST /auth/oauth/complete` answers `{kind: "login", login: LoginResponse}` for a linked identity (two-factor still applies), `{kind: "register", registration}` for a new one, or `{kind: "linked", provider}` after a link. A new identity whose verified email belongs to an existing account is not merged automatically (that would let a provider take over the account): registration answers 50035 `email` and the user links the provider from My Account instead. Linking an identity that belongs to another account fails with `error`. Unlinking the last sign-in method of an account without a password is refused.

Security rules (review of PR #10):
- Identity check for sensitive actions (account edits, setting a first password, disable, delete, enabling two-factor, viewing or regenerating backup codes): accounts with a password send `password`. Accounts without a password send `code` (TOTP or backup) when two-factor is on. Otherwise the session must have signed in with, or re-confirmed through, a linked provider in the last 5 minutes; if not, the answer is 400 50035 `reauth`. To re-confirm, the client runs `POST /auth/oauth/{id}/authorize {link: true}` for a provider that is already linked; `complete` answers `{kind: "reauthenticated", provider}` and marks the calling session fresh. Disable and delete also need `code` when two-factor is on (password accounts).
- Linking: the callback only records a pending `link` result. The identity is written in `/auth/oauth/complete`, after the client verifier is checked and only when the caller's token belongs to the user who started the link (otherwise 400 `code`), so a provider URL sent to someone else links nothing.
- Pre-hijack: linking a new provider and enabling two-factor need a verified email (400 50035 `email`). A password reset of an account whose email was not verified yet also removes every linked provider, because the reset proves the inbox and the links may belong to whoever created the account.
- Password changes and resets cancel a pending email change (the pending address and its verification links); a change requested in the same call is kept.
- Failed second-factor codes are counted per account across tickets and routes: 10 failures in 15 minutes, then 429 until the window passes.
- `/auth/forgot` does its work after answering, so known and unknown logins take the same time.
- Invalid `VOKKO_SMTP_*` settings stop the server at start; mail goes to the log only when `VOKKO_SMTP_HOST` is unset.

Security rules, round 2:
- Linking a new provider needs the identity check. Accounts with a password or with two-factor send `password` / `code` in `OAuthAuthorizeRequest` together with `link: true` (checked at authorize). Accounts with neither need a session that is fresh (under 5 minutes) when `complete` inserts the identity. Authorize cannot know yet whether the provider account is new, so accounts with a password or two-factor also send `password` / `code` to re-confirm an already-linked provider; for accounts with neither, re-confirming needs no credentials (it is how they get a fresh session).
- Second-factor attempts are recorded before they are counted, so parallel requests cannot get past the 10-per-15-minutes limit.
- `users.email_verified_at` stores when the account's email was first verified (verify link, reset, or a provider-verified sign-up); later email changes keep it. A password reset removes every provider link made before that time (all of them if the email was never verified). Verifying an email never removes sign-in methods. Otherwise a reset only changes the password: providers linked after the email was verified stay linked and keep signing in (as on Discord).
- Any `VOKKO_SMTP_*` variable without `VOKKO_SMTP_HOST` stops the server at start.
- Reset mail goes out at most once a minute per account.
- Registration answers "Already taken." for an existing email or username. This leaks that the account exists; it is a deliberate trade-off (Discord does the same) for a usable sign-up form, and `/auth/*` rate limits slow down scraping.

## Voice (V1, docs/design/voice.md)

Media goes through a self-hosted LiveKit SFU; vokko-server only checks permissions, mints LiveKit tokens, keeps the in-memory voice-state table and listens to LiveKit webhooks. Voice is enabled when `VOKKO_LIVEKIT_URL`, `VOKKO_LIVEKIT_API_KEY` and `VOKKO_LIVEKIT_API_SECRET` are set (optional `VOKKO_LIVEKIT_API_URL`, default derived from the URL: `wss` → `https`; `VOKKO_VOICE_BITRATE_MAX`, default 128000, at most 384000). READY carries `media: InstanceMediaConfig` (`voice_enabled` false when unset).
- Channels: guild voice channels (type 2) always carry `bitrate` (default 64000) and `user_limit` (default 0 = unlimited). Create/PATCH accept both on voice channels only (400 50035 elsewhere); `bitrate` must be 8000..`voice_bitrate_ceiling` (V1 has no per-guild media settings, so the guild maximum equals the instance ceiling), `user_limit` 0..99, else 400 50035.
- Op 4 checks, in order: voice configured (`media_unavailable`), channel is a guild voice or stage channel the user can see with CONNECT, or a DM / group DM the user is a recipient of (`missing_permissions`; DM rules under DM calls), not timed out (`timed_out`), `user_limit` (`channel_full`; MOVE_MEMBERS bypasses; not on stages). A refusal dispatches `VOICE_CONNECT_FAILED {guild_id, channel_id, reason}` to the requesting gateway session only and changes nothing. Op 4 is limited to 30 per minute per session (close 4008).
- Success: `VOICE_SERVER_UPDATE {guild_id, channel_id, endpoint, token, session_id}` to the requesting session only (`session_id` names the voice session the token is for; clients adopt only their own), then `VOICE_STATE_UPDATE` (with `member`) to everyone who can see the channel. Room `v<channel_id>`, participant identity = user id, token valid 10 minutes, grants from permissions: `roomJoin`, `canSubscribe`, `canPublishSources` = `microphone` with SPEAK, `camera`/`screen_share`/`screen_share_audio` with STREAM; `canPublishData` and `canUpdateOwnMetadata` false. Without SPEAK the state has `suppress: true`.
- Every new binding (first join, move, join from another gateway session or device) gets a new voice `session_id`; a client that sees its own user in VOICE_STATE_UPDATE with a `session_id` it did not ask for was moved to another device and disconnects. The same session toggling self mute/deafen gets VOICE_STATE_UPDATE only, no new token; the same session re-sending an unchanged op 4 (reconnecting to LiveKit) gets a fresh VOICE_SERVER_UPDATE for the same voice `session_id` and nothing is broadcast. A move to another channel sends `channel_id: null` for the user to those who could see the old channel but not the new one.
- Lifecycle: the state is dropped (and `channel_id: null` broadcast) when the client leaves, when no LiveKit `participant_joined` arrives within 30 s of the token being issued (`VOKKO_VOICE_CONNECT_TIMEOUT_SECS`, default 30), when LiveKit reports `participant_left` for the current session, or when its gateway session is gone for 60 s without a resume or re-identify that re-sends op 4. A re-identified client re-sends op 4 for its channel and is re-bound without a leave in between.
- `POST /internal/livekit/webhook` (server root, not under `/api/v1`, no CORS): LiveKit only; the `Authorization` JWT must be signed with the API secret and carry `sha256` = base64 SHA-256 of the body, else 401. Events are matched by identity, room and participant metadata `session_id`; stale or duplicate events change nothing. The server reconciles with LiveKit's RoomService every 60 s and rebuilds the table from it on start (restored states wait 60 s for their client to re-send op 4). When LiveKit cannot be reached at start, the restore is retried with backoff (1 s doubling to 60 s) and reconciliation removes no LiveKit participant until a restore has succeeded.
- Every token carries a fresh nonce in the participant metadata; LiveKit's `participant_joined` / `participant_left` only count for the latest token of the session, so a reconnect's old connection leaving (in either order) never ends the state. Reconciliation also removes LiveKit participants in `v<id>` rooms that match no state (states younger than 15 s are spared), and ends a state LiveKit no longer lists only if no newer token was issued for it meanwhile, so a failed `RemoveParticipant` after a kick does not leave anyone behind.
- Voice channel status: guild voice channels carry `status` (`null` when unset). `PUT /channels/{id}/voice-status` sets it; `VOICE_CHANNEL_STATUS_UPDATE {id, guild_id, status}` goes to the channel's viewers; it is cleared (event with `null`) when the last person leaves.
- READY guilds and GUILD_CREATE carry `voice_states` for the guild's voice channels the receiver can see. Speaking state never goes through the gateway (clients in the call get it from LiveKit).
- Server mute / deafen / move (`PATCH /guilds/{id}/members/{uid}`, Discord's keys): `mute` needs MUTE_MEMBERS, `deaf` DEAFEN_MEMBERS (deafen also stops subscribing, so a server-deafened member sees no cameras or streams either; known difference from Discord, where deafen only cuts audio; it does not imply mute in the stored flags, but a deafened member cannot publish the microphone either). Both persist on the member (GuildMember `mute`/`deaf`, absent = false) across leave/rejoin and show in VoiceState `mute`/`deaf`; the server applies them to a connected member through LiveKit `UpdateParticipant` (microphone dropped from `canPublishSources`, `canSubscribe` false when deafened) and mutes the published microphone track. `channel_id` needs MOVE_MEMBERS in the member's current channel and in the target; the target must be a voice or stage channel of the guild the member may join (VIEW_CHANNEL + CONNECT, not timed out; 403 50013 otherwise), `user_limit` does not apply. The moved member keeps the voice `session_id`, leaves the old LiveKit room and gets VOICE_SERVER_UPDATE for the new channel on the gateway session that owns the state. `channel_id: null` disconnects. A member who is not in voice → 400 40032. No role hierarchy applies to voice moderation (as in Discord).
- Mid-call eviction: a timeout, losing VIEW_CHANNEL or CONNECT (role edit or delete, member roles, channel overwrite, category sync), a kick or a ban ends the member's voice state (`channel_id: null`) and removes them from LiveKit. Losing or gaining SPEAK / STREAM (or a server mute/deafen change) updates the participant's publish rights through `UpdateParticipant` without a reconnect; `suppress` follows SPEAK in voice channels.

## Stage channels (type 13)

- A stage channel is a voice room (`v<channel_id>`) with speakers and an audience. Op 4 accepts it like a voice channel (VIEW_CHANNEL + CONNECT; `user_limit` does not apply). Everyone joins as audience: `suppress: true`, a token without publish sources, LiveKit `hidden` (audience members are not visible participants; clients list them from voice states).
- Stage moderator = MANAGE_CHANNELS + MUTE_MEMBERS + MOVE_MEMBERS in the channel (Discord's set). Only moderators create, edit and end a stage instance; `topic` 1-120 characters (400 50035), `privacy_level` 2 only. A second instance in the same channel → 400 150006. STAGE_INSTANCE_CREATE/UPDATE/DELETE go to everyone who can see the channel; READY guilds and GUILD_CREATE carry `stage_instances`.
- Raise hand: `PATCH /guilds/{id}/voice-states/@me {channel_id, request_to_speak_timestamp}` (ISO time, the server stores its own clock; `null` lowers it), needs REQUEST_TO_SPEAK; the caller must be in that stage (400 40032 otherwise). Becoming a speaker yourself (`suppress: false` on @me) needs stage moderator; `suppress: true` (back to the audience) needs nothing. `PATCH /guilds/{id}/voice-states/{uid} {channel_id, suppress}`: moderator only (403 50013), invites to speak (`false`) or moves back to the audience (`true`). Promotion clears the raised hand and grants the microphone with SPEAK (camera/screen with STREAM) through `UpdateParticipant` (and un-hides); demotion takes them away. Each change is a VOICE_STATE_UPDATE.
- The stage ends (STAGE_INSTANCE_DELETE, every speaker back to the audience, raised hands cleared) on `DELETE /stage-instances/{channel_id}` or when the last stage moderator leaves the channel while an instance exists. Deleting the channel deletes its instance.

## DM calls (V3, docs/design/voice.md §4.2)

A DM or group DM is a voice-capable channel: op 4 with `guild_id: null` and the DM's `channel_id` joins its call, through the same LiveKit setup as guild voice (room `v<channel_id>`, tokens, webhooks, reconciliation, 15 s connect timeout, 60 s gateway grace). Voice states of a DM call have `guild_id: null`, no `member`, and go to the DM's recipients only. Every recipient may connect, speak and publish camera / screen share (no Nitro gates, no permission bits in DMs).
- **Call object** (`Call`): `channel_id`, `message_id` (the type 3 message), `region` (`null` = automatic; Vokko has one media server, so it is stored and echoed only), `ringing` (user ids being rung now), `voice_states`. CALL_CREATE carries the whole object; CALL_UPDATE the same without `voice_states`; CALL_DELETE `{channel_id}`. All three go to every recipient of the DM. After READY the server sends CALL_CREATE for every ongoing call in the user's DMs (READY itself has no DM voice states).
- **Starting**: the first op 4 into a DM with no call creates the call: a type 3 `Call` message authored by the caller (`call: {participants: [caller], ended_timestamp: null}`, no mention or unread counter bump; it reopens a closed DM like any message), then CALL_CREATE with every other recipient in `ringing`, then the caller's VOICE_STATE_UPDATE. A later joiner is added to `call.participants` (MESSAGE_UPDATE) and taken out of `ringing` (CALL_UPDATE).
- **Ringing** lasts 3 minutes (`CALL_RING_TIMEOUT_SECS`; the server setting `call_ring_timeout` exists for tests), then that user is taken out of `ringing` (CALL_UPDATE); a user who never joined sees the call as missed. `POST /call/ring` rings again (restarts the 3 minutes) and needs an ongoing call (400 50035 otherwise) that you are in (403 50013 otherwise); users currently in the call are skipped (someone who joined and left is rung again). It is limited to 5 rings, then one every 5 s, per user. `POST /call/stop-ringing` without `recipients` declines for yourself; stopping someone else's ringing needs you to be in the call (403 50013). Unknown or non-recipient ids → 400 50035.
- **Blocks follow the DM's message rules** ("no ringing if you couldn't message them"): in a 1:1 DM a block in either direction refuses op 4 (`VOICE_CONNECT_FAILED` reason `blocked`) and ringing (403 50007). In a group DM recipients who blocked the caller or whom the caller blocked are left out of the automatic ring list, and naming one in `POST /call/ring` → 403 50007; joining a group DM call is not affected by blocks.
- **Ending**: when the last participant leaves (leave, timeout, gateway loss, LiveKit `participant_left` / `room_finished`, leaving the group DM) the call ends: `call.ended_timestamp` is written (MESSAGE_UPDATE), ringing stops and CALL_DELETE is sent. Duration = `ended_timestamp` − the message `timestamp`. On server start, calls whose room has nobody left are ended the same way.
- **Limits**: at most 10 people in one call (`CALL_PARTICIPANT_MAX`, op 4 → `channel_full`) and 25 published video streams (cameras + screen shares, `CALL_VIDEO_MAX`; with 10 people at most 20 can exist, so the participant cap enforces it). Leaving a group DM (`DELETE /channels/{id}`) also leaves its call and stops ringing that user.
- Errors: 50007 blocked, 50035 no call / bad recipients / bad region (`region` is `null` or 1-32 chars of `a-z 0-9 -`), 50013 stopping someone else's ringing from outside the call, 50001 not a recipient.

## Proposed (client built against the mock only; the server does not implement these)

- `GET /status` (no auth, no rate limit; outside the guild/channel resources): `200 {maintenance: {message, starts_at} | null}`. `message` is a short plain-text notice (max 280 chars); `starts_at` is an ISO-8601 time when the work is scheduled, or `null` when it is under way. The client shows it as a dismissible top banner ("Maintenance: ..." or "Scheduled maintenance: ... Starts <time>"), polls it every 60 s and after every READY, and treats any error or 404 as "no notice". The desktop client only calls it against the mock (and when built with `VITE_VOKKO_STATUS=1`), so a server that never ships it sees no extra traffic. An operator-set notice could come from a server setting or an admin endpoint; none is specified here.
